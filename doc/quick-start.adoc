[#trystero-quick-start]
== Quick start

The quick start is one native program with two peers in it, `alice` and
`bob`: each is an app of its own, with an id the program gives it, and both
join the room `lobby` of the app `webcpp-trystero-quick-start`. alice greets
bob when he joins, bob answers, each prints what it received, and both
leave, which ends the program. In the browser the same rooms run in a page,
as the chat example shows (<<trystero-quick-start-browser>>).
<<trystero-building-examples>> builds and runs both.

[#trystero-quick-start-native]
=== Two peers in one program

An app is one peer: its id among the peers, its relays and its STUN servers.
The program gives each app its id, `app_config::self_id`, where an app would
draw 20 random characters, so that what it prints is the same on every run.
It meets over the relay whose URL is in the environment,
`TRYSTERO_RELAY_URL`, which the lane `relayed` starts on 127.0.0.1, and
then keeps its peers on the machine; without it, the program uses
Trystero's public relays and STUN servers, as every program that names none
does:

[source]
----
include::{examples}/quick_start.cpp[tag=includes]

include::{examples}/quick_start.cpp[tag=config]
----

`main` makes one `platform::backend` for both apps, joins each app to the
room, and makes in each room the action `chat`, whose messages are
`std::string`. alice greets each peer that joins, once its handshake
completes, with a message to that peer alone, and prints what she receives,
after its sender's id, then leaves. bob's part is a coroutine. `run`
returns once no work is left: each room closes its relays as it leaves, and
each connection closes as soon as no room uses it:

[source]
----
include::{examples}/quick_start.cpp[tag=main]
----

bob awaits the first message with `async_receive`, prints it after its
sender's id, answers its sender with `async_send`, and leaves with
`async_leave`. `asio::as_tuple` hands each error over as a value, so a
room left first ends the wait instead of throwing:

[source]
----
include::{examples}/quick_start.cpp[tag=answer]
----

The program prints bob's line, then alice's:

[listing]
----
include::{examples}/quick_start.expected[]
----

Its twin on Trystero JS prints the same two lines. Trystero draws one
`selfId` per page, so bob is a second page there, and each peer prints the
other's name where the {cpp} program prints the id it gave the app:

[source,javascript]
----
include::{twins}/quick_start.mjs[lines=7..]
----

=== In the browser

In a page the same app and room are {cpp} compiled to WebAssembly, over the
page's own WebSocket and `RTCPeerConnection`. The chat example keeps what a
page's program keeps for as long as the page lives: an `io_context`, the
`platform::backend` on its executor, the app, the room joined through it,
and its actions:

[source]
----
include::{examples}/chat/chat.cpp[tag=state]
----

<<trystero-platform-chat>> shows how it joins, sends, and runs its
`io_context` from `main`, and <<trystero-building-examples>> serves it.
Two tabs of the chat that join the same app and room meet; so do a native
peer and a page, which the lane `interop` proves with Trystero JS pages in
headless Chrome (<<trystero-testing-lanes>>).
