[#trystero-quick-start]
== Quick start

The two smallest programs that join a room: one for the browser, one native.
Both use an empty app password and join the room `lobby` of
`webcpp-trystero-quick-start`, so they
meet each other, and any Trystero JS page that joins the same room,
`joinRoom({appId: 'webcpp-trystero-quick-start'}, 'lobby')`, meets them
both. <<trystero-building-examples>> builds and runs them.

[#trystero-quick-start-browser]
=== In the browser

A browser program keeps four things alive for as long as its page: an
`io_context`, the `platform::backend` that implements the platform over the
page's own objects on the executor of that `io_context`, the app that owns its
identity and shared connections, and the room joined through that app.
Actions are made from the room by name and payload type:

[source]
----
include::{examples}/quick_start.cpp[tag=includes]

include::{examples}/quick_start.cpp[tag=application]
----

Handlers are set once the application exists. This program greets every peer
that completes the handshake, prints every `chat` message, starts a
coroutine that answers the `echo` action, and runs the `io_context`:

[source]
----
include::{examples}/quick_start.cpp[tag=main]
----

The coroutine awaits messages with `async_receive` and answers with
`async_send`. `webcpp::asio::as_tuple` turns the error into a value, so
leaving the room ends the loop instead of throwing:

[source]
----
include::{examples}/quick_start.cpp[tag=coroutine]
----

`main` runs the `io_context` for as long as the page lives, as a native
program does, under a work guard, since a page that waits for its peers may
have no work of its own. Nothing blocks the browser: whenever nothing is
ready, `run` suspends into the browser's event loop, and every JavaScript
event that reaches the library is posted to the `io_context`, whose handlers
run when `run` resumes (<<trystero-platform-page>>).

[#trystero-quick-start-native]
=== Natively

The same app and its joined room, natively, whole: a program that greets every peer that joins
and prints what it receives on `chat`, over the same `platform::backend`. A native program runs
its `io_context` as the browser's does, and webcpp::webrtc posts what
libdatachannel's threads report to it:

[source]
----
include::{examples}/native_quick_start.cpp[tag=program]
----

`io.run()` returns only when the program is stopped: the room keeps its
relays and its peers for as long as it lives.
