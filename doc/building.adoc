[#trystero-building]
== Building

trystero is header-only, and is developed inside the webcpp superproject, as
a Boost library is developed inside Boost. It builds on three libraries of
webcpp's: webcpp::asio; webcpp::webrtc, the platform backend's WebRTC; and
webcpp::beast, its relays' WebSockets, on both targets.
Its native TLS and WebRTC dependencies are built from pinned sources. Only
libsecp256k1 needs an external installation:

[cols="2,2,3",options="header"]
|===
| Library | Needed by | Found where

| libsecp256k1 0.8.0, with its `schnorrsig` and `extrakeys` modules
| every room: it signs the Nostr events peers meet through
| `-sSECP256K1_ROOT=<dir>` natively, else `.local/secp256k1-native`;
  `-sSECP256K1_EMSCRIPTEN_ROOT=<dir>` for its emscripten build, else
  `.local/secp256k1-emscripten`

| webcpp::asio
| every room
| `/webcpp/asio//asio`: natively Boost.Asio, on emscripten the backend it ships

| webcpp::webrtc
| the platform backend's WebRTC, on both targets
| `/webcpp/webrtc//webrtc`, the superproject's `libs/webrtc`

| webcpp::beast
| the platform backend's relays: their WebSockets, and natively their TLS
| `/webcpp/beast//tls` natively, Boost.Beast over the source-built OpenSSL;
  `/webcpp/beast//browser` in a page, over the page's `WebSocket`

| Boost.URL
| the platform backend's relays: their URLs, on both targets
| `/webcpp//boost_url`, built from Boost's sources once per variant

| libdatachannel 0.24.6
| the platform backend natively, through webcpp::webrtc
| `/webcpp/third_party//libdatachannel`, built from `third_party/libs/libdatachannel`

| OpenSSL 3.5.9
| the platform backend natively: its WebRTC, its relays' TLS, its sealer and
  its randomness
| `/webcpp/third_party//openssl`, shared by the Asio, Beast and Trystero build graphs
|===

The libsecp256k1 `-s` option names a directory with the library's `include/` and `lib/`, on b2's
command line; the environment is never read, so that a variable a shell keeps
from another day never replaces `.local/` without a word. Without it, the
library is looked for in the directory of `.local/` that the table names,
where webcpp's continuous integration installs it, when that directory holds
the library's header, and else, natively outside Windows, in `/usr/include`
or `/usr/local/include`, where a system install is legitimate. A relative
`-s` is read from b2's working directory. A `-s` that names a directory without the library's
header stops the build, naming it. A library found nowhere leaves trystero
out: its tests and examples are skipped, the build says so once, naming the
library and where it looked, and every other library builds; with
`webcpp-require-external=on`, as the continuous integration builds, it stops
the build instead. With MSVC, libsecp256k1 uses CMake's
`libsecp256k1.lib`, linked statically with `SECP256K1_STATIC` defined.
trystero's `build.jam` declares that external dependency so:

[listing]
----
include::{library-root}/build.jam[tag=dependencies]
----

[#trystero-building-project]
=== In a b2 project

A program uses trystero through `/webcpp/trystero//platform`, the rooms and
the platform backend (<<trystero-platform>>), on either target: natively,
built with `threading=multi`, and in a page. `/webcpp/trystero//trystero`
is the rooms alone, which adds trystero's headers, Boost's, webcpp::asio,
libsecp256k1 and webcpp::document with Boost.JSON's and Boost.Charconv's
definitions, compiled once per variant, and no
WebRTC on any target: a program that runs its rooms over a backend of its
own, as trystero's tests run whole rooms over the memory relays
(<<trystero-testing-program>>), needs no more:

[listing]
----
include::{library-root}/build.jam[tag=trystero]
----

On emscripten webcpp::asio builds without threads, since the page has none,
links embind, and links its runtime in the suspension variant the build
asks, `webcpp-suspend=jspi` by default or `asyncify`; a program is named
after it, as the chat's `chat-program-60-d-jspi.js`. embind is linked as a
flag, `-lembind`, rather than with b2's own `<embind>on`: that feature is
not free, and b2 ignores a feature that is not free among usage
requirements, so a program that used it would not link.

`/webcpp/trystero//platform` adds the platform backend to the rooms, with an
alternative for each target. Natively it adds webcpp::webrtc, with
libdatachannel and the same source-built OpenSSL used by Asio and Beast;
webcpp::beast's TLS over that OpenSSL for the relays' WebSockets,
`/webcpp/beast//tls`; Boost.URL, which reads the relays' URLs; and
webcpp::asio's `//tls`, whose `make_tls_client_context()` gives a program
webcpp's embedded authorities in place of the system's, which the backend
trusts by default (<<trystero-platform-relays>>). In a page it adds
webcpp::webrtc, over the page's own `RTCPeerConnection`; webcpp::beast's
`//browser`, over the page's `WebSocket`; and Boost.URL, which reads the
relays' URLs there too. A page links no OpenSSL:

[listing]
----
include::{library-root}/build.jam[tag=platform]
----

Natively the platform backend's WebRTC, libdatachannel's, uses worker
threads, so each consumer declares `<threading>multi`. Its OpenSSL
dependency is the matching threaded variant; a single-threaded native
program that uses the backend is rejected before compilation, with an error
that says to add `<threading>multi`. A page has no threads, and needs none.

The platform backend works with exceptions and without them
(<<trystero-platform-exceptions>>), so a program builds as it asks, as the
examples do, the quick start natively with `<threading>multi`, which the
build runs over a relay of its own (<<trystero-building-examples>>):

[listing]
----
include::{examples}/Jamfile[tag=quick-start]
----

and as trystero's own tests of the platform backend do, on each target that
builds them, once without exceptions too:

[listing]
----
include::{library-root}/test/Jamfile[tag=platform]
----

A page's program is linked for the web, with a memory that grows, as the
chat's is:

[listing]
----
include::{examples}/chat/Jamfile[tag=page]
----

[#trystero-building-emscripten]
=== The emscripten toolset

The emscripten target is b2's `emscripten` toolset, registered against
Emscripten 6.0.11 from emsdk, as a `user-config.jam` declares it, where
`$(emsdk)` is the emsdk's directory and `$(node)` the node that runs a
program:

[listing]
----
include::{webcpp-root}/tools/ci/emsdk.jam[tag=emsdk]
include::{webcpp-root}/tools/ci/emsdk.jam[tag=emscripten]
----

With it, libsecp256k1 installed and the pinned source submodules initialized, from the root of a webcpp checkout,
these build the tests and the examples, natively and on emscripten:

[source,bash]
----
b2 libs/trystero/test libs/trystero/example
b2 toolset=emscripten libs/trystero/test libs/trystero/example
----

[#trystero-building-dependencies]
=== Preparing the dependencies

libsecp256k1 is built twice: natively, and with Emscripten for the browser.
Its small tables keep the browser's download small:

[source,bash]
----
git clone --branch v0.8.0 https://github.com/bitcoin-core/secp256k1.git
options="-DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF \
  -DSECP256K1_ENABLE_MODULE_SCHNORRSIG=ON -DSECP256K1_ENABLE_MODULE_EXTRAKEYS=ON \
  -DSECP256K1_ECMULT_WINDOW_SIZE=4 -DSECP256K1_ECMULT_GEN_KB=2 \
  -DSECP256K1_BUILD_TESTS=OFF -DSECP256K1_BUILD_EXHAUSTIVE_TESTS=OFF \
  -DSECP256K1_BUILD_BENCHMARK=OFF"

cmake -S secp256k1 -B build-secp256k1-native $options \
  -DCMAKE_INSTALL_PREFIX=$PWD/webcpp/.local/secp256k1-native
cmake --build build-secp256k1-native && cmake --install build-secp256k1-native

emcmake cmake -S secp256k1 -B build-secp256k1-emscripten $options \
  -DCMAKE_INSTALL_PREFIX=$PWD/webcpp/.local/secp256k1-emscripten
cmake --build build-secp256k1-emscripten && cmake --install build-secp256k1-emscripten
----

where `webcpp` is the checkout of the superproject: each is installed in the
directory of `.local/` where the build looks for it.

Initialize the native dependencies from the superproject root:

[source,bash]
----
git submodule update --init --recursive third_party/libs/openssl third_party/libs/libdatachannel
----

Install CMake 3.21 or newer, Perl and Make (native Windows Perl and nmake
with MSVC). B2 builds OpenSSL, libdatachannel and its pinned nested
libjuice, usrsctp and libsrtp sources for the configured compiler, standard
library, runtime and build variant. Upstream sources are verified and
copied to a disposable build directory; the checkout is never patched.
The resulting headers and separate static archives stay in B2's variant
directory, and the final link contains exactly one OpenSSL archive pair.

libdatachannel's own WebSocket, examples and tests are disabled; media
transport remains enabled. System OpenSSL and installed libdatachannel
binaries are never fallback providers. A combined Asio/Beast/Trystero
application uses the same native `<threading>multi` configuration for all
three libraries.

[#trystero-building-examples]
=== Running the examples

The quick start and the programs of the appendix "Differences"
(<<trystero-differences>>) run natively in the lane `relayed`, each over a
Nostr relay of its own on 127.0.0.1, which `example/run_over_relay.mjs`
starts and names to the program in `TRYSTERO_RELAY_URL`: a program passes
when it ends by itself having printed its `.expected`. Node runs the relay,
with the packages `test/oracle` pins. The first command runs the lane, the
second the quick start alone:

[source,bash]
----
b2 libs/trystero/example//relayed
b2 libs/trystero/example//quick_start
----

The quick start's executable stays under the build directory. Run without
`TRYSTERO_RELAY_URL`, it meets over Trystero's public relays and STUN
servers, as a program that names none does, and prints the same two lines
(<<trystero-quick-start-native>>) within seconds, then ends:

[source,bash]
----
`find bin/libs/trystero/example/quick_start.test -name quick_start -type f`
----

The chat needs a browser, so the build links its program and never runs it
(<<trystero-platform-chat>>). The target `site` copies the page and its
program into a directory of its own under the build directory, out of the
tree, and prints it. The page is served from `localhost`, where
`crypto.subtle` exists:

[source,bash]
----
b2 toolset=emscripten libs/trystero/example/chat//site
python3 -m http.server 8000 -d `find bin/libs/trystero/example/chat -name site -type d`
----

At http://localhost:8000, two tabs that join the same app and room, the
page's `webcpp-trystero-chat` and `lobby` unless their user changes them,
meet over the public relays within seconds: each counts the other as a peer,
and what one sends appears in the other. On another toolset, `site` stops
the build, saying that the page is built on emscripten alone.
