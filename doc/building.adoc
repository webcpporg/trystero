[#trystero-building]
== Building

trystero is header-only, and is developed inside the webcpp superproject, as
a Boost library is developed inside Boost. Its native TLS and WebRTC
dependencies are built from pinned sources. Only libsecp256k1 needs an
external installation:

[cols="2,2,3",options="header"]
|===
| Library | Needed by | Found where

| libsecp256k1 0.8.0, with its `schnorrsig` and `extrakeys` modules
| every room: it signs the Nostr events peers meet through
| `-sSECP256K1_ROOT=<dir>` natively, else `.local/secp256k1-native`;
  `-sSECP256K1_EMSCRIPTEN_ROOT=<dir>` for its emscripten build, else
  `.local/secp256k1-emscripten`

| libdatachannel 0.24.6
| the native backend
| `/webcpp/third_party//libdatachannel`, built from `third_party/libs/libdatachannel`

| OpenSSL 3.5.9
| the native backend
| `/webcpp/third_party//openssl`, shared by the Asio, Beast and Trystero build graphs
|===

The libsecp256k1 `-s` option names a directory with the library's `include/` and `lib/`, on b2's
command line; the environment is never read, so that a variable a shell keeps
from another day never replaces `.local/` without a word. Without it, the
library is looked for in the directory of `.local/` that the table names,
where webcpp's continuous integration installs it, when that directory holds
the library's header, and else, natively outside Windows, in `/usr/include`
or `/usr/local/include`, where a system install is legitimate. A relative
`-s` is read from b2's working directory. A `-s` that names a directory without the library's
header stops the build, naming it. A library found nowhere leaves trystero
out: its tests and examples are skipped, the build says so once, naming the
library and where it looked, and every other library builds; with
`webcpp-require-external=on`, as the continuous integration builds, it stops
the build instead. With MSVC, libsecp256k1 uses CMake's
`libsecp256k1.lib`, linked statically with `SECP256K1_STATIC` defined.
trystero's `build.jam` declares that external dependency so:

[listing]
----
include::{library-root}/build.jam[tag=dependencies]
----

[#trystero-building-project]
=== In a b2 project

A b2 project uses the rooms and the browser backend through
`/webcpp/trystero//trystero`, which adds trystero's headers, Boost's,
libsecp256k1 and Boost.JSON's definitions, compiled once per variant, and,
on emscripten, embind and `BOOST_ASIO_DISABLE_THREADS`, since the page has no
threads:

[listing]
----
include::{library-root}/build.jam[tag=trystero]
----

embind is linked as a flag, `-lembind`, rather than with b2's own
`<embind>on`: that feature is not free, and b2 ignores a feature that is not
free among usage requirements, so a program that used it would not link.

A native program uses `/webcpp/trystero//native`, which adds libdatachannel
and the same source-built OpenSSL used by Asio and Beast:

[listing]
----
include::{library-root}/build.jam[tag=native]
----

The native backend uses worker threads, so each consumer declares
`<threading>multi`. Its OpenSSL dependency is the matching threaded variant;
a single-threaded native backend is rejected before compilation.

The native backend's WebRTC also needs exceptions (<<trystero-native-exceptions>>),
and b2 lets no usage requirement override a build's
`exception-handling=off`, so each program and test that uses it declares
`<exception-handling>on` itself, as the examples do:

[listing]
----
include::{examples}/Jamfile[tag=native]
----

and as trystero's own tests of the native backend's connections do:

[listing]
----
include::{library-root}/test/Jamfile[tag=native]
----

A browser program is linked for the web, with a memory that grows:

[listing]
----
include::{examples}/Jamfile[tag=browser]
----

[#trystero-building-emscripten]
=== The emscripten toolset

The emscripten target is b2's `emscripten` toolset, registered against
Emscripten 6.0.11 from emsdk, as a `user-config.jam` declares it, where
`$(emsdk)` is the emsdk's directory and `$(node)` the node that runs a
program:

[listing]
----
include::{webcpp-root}/tools/ci/emsdk.jam[tag=emsdk]
include::{webcpp-root}/tools/ci/emsdk.jam[tag=emscripten]
----

With it, libsecp256k1 installed and the pinned source submodules initialized, from the root of a webcpp checkout,
these build the tests and the examples, natively and on emscripten:

[source,bash]
----
b2 libs/trystero/test libs/trystero/example
b2 toolset=emscripten libs/trystero/test libs/trystero/example
----

[#trystero-building-dependencies]
=== Preparing the dependencies

libsecp256k1 is built twice: natively, and with Emscripten for the browser.
Its small tables keep the browser's download small:

[source,bash]
----
git clone --branch v0.8.0 https://github.com/bitcoin-core/secp256k1.git
options="-DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=OFF \
  -DSECP256K1_ENABLE_MODULE_SCHNORRSIG=ON -DSECP256K1_ENABLE_MODULE_EXTRAKEYS=ON \
  -DSECP256K1_ECMULT_WINDOW_SIZE=4 -DSECP256K1_ECMULT_GEN_KB=2 \
  -DSECP256K1_BUILD_TESTS=OFF -DSECP256K1_BUILD_EXHAUSTIVE_TESTS=OFF \
  -DSECP256K1_BUILD_BENCHMARK=OFF"

cmake -S secp256k1 -B build-secp256k1-native $options \
  -DCMAKE_INSTALL_PREFIX=$PWD/webcpp/.local/secp256k1-native
cmake --build build-secp256k1-native && cmake --install build-secp256k1-native

emcmake cmake -S secp256k1 -B build-secp256k1-emscripten $options \
  -DCMAKE_INSTALL_PREFIX=$PWD/webcpp/.local/secp256k1-emscripten
cmake --build build-secp256k1-emscripten && cmake --install build-secp256k1-emscripten
----

where `webcpp` is the checkout of the superproject: each is installed in the
directory of `.local/` where the build looks for it.

Initialize the native dependencies from the superproject root:

[source,bash]
----
git submodule update --init --recursive third_party/libs/openssl third_party/libs/libdatachannel
----

Install CMake 3.21 or newer, Perl and Make (native Windows Perl and nmake
with MSVC). B2 builds OpenSSL, libdatachannel and its pinned nested
libjuice, usrsctp and libsrtp sources for the configured compiler, standard
library, runtime and build variant. Upstream sources are verified and
copied to a disposable build directory; the checkout is never patched.
The resulting headers and separate static archives stay in B2's variant
directory, and the final link contains exactly one OpenSSL archive pair.

libdatachannel's own WebSocket, examples and tests are disabled; media
transport remains enabled. System OpenSSL and installed libdatachannel
binaries are never fallback providers. A combined Asio/Beast/Trystero
application uses the same native `<threading>multi` configuration for all
three libraries.

[#trystero-building-examples]
=== Running the examples

The three examples need the public relays or a browser, so the build links
them and never runs them: `native_quick_start.cpp`, natively;
`quick_start.cpp`, a `.js` and a `.wasm` to embed in a page; and the chat,
a page whose room is {cpp} (<<trystero-browser-chat>>). The quick starts
meet in the room `lobby` of the app `webcpp-trystero-quick-start`, over the
public relays; the chat joins the app and the room its user types, the room
`lobby` of the app `webcpp-trystero-chat` unless the user changes them, and
meets the quick starts when the user types theirs.

The native quick start is built as a program of its own, and runs until it
is stopped:

[source,bash]
----
b2 libs/trystero/example//native_quick_start-program
`find bin/libs/trystero/example -name native_quick_start-program -type f`
----

The chat is a page and its program, which the target `site` copies into a
directory of its own under the build directory, out of the tree, and prints.
The page is served from `localhost`, where `crypto.subtle` exists:

[source,bash]
----
b2 toolset=emscripten libs/trystero/example/chat//site
python3 -m http.server 8000 -d `find bin/libs/trystero/example/chat -name site -type d`
----

At http://localhost:8000, joining the app `webcpp-trystero-quick-start`, in
place of the page's `webcpp-trystero-chat`, and the room `lobby` brings the
native quick start in as a peer within seconds: its greeting appears in the
chat, and what the page sends is printed in its terminal. On another toolset, `site` stops the build, saying that the page is
built on emscripten alone.
