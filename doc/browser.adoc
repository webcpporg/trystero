[#trystero-browser]
== The browser backend

In the browser, `browser::backend` implements the backend interface over the
page's own `WebSocket` and `crypto.subtle`, over webcpp::asio's timers, and
over the page's `RTCPeerConnection` and `RTCDataChannel` through
webcpp::webrtc (<<trystero-design-backend-webrtc>>). It is given the
executor of the program's `io_context`, which the program runs from `main`,
as webcpp::asio's model has it. One backend serves every app and room of
the page. Apps with different passwords use distinct self ids and share no
connection or presence.

[#trystero-browser-run]
=== The program runs its io_context

A page's program is the shape of any program of webcpp::asio: `main` makes
the `io_context`, the backend, the app and its rooms, and calls `io.run()`,
which runs the rooms' handlers on the stack of `main` and suspends into the
browser's event loop whenever nothing is ready (webcpp::asio's run family,
in either suspension variant).

* The page's events reach {cpp} through webcpp::asio's bridge, a service of
  the `io_context`: a socket's open, message or close, a settled Web Crypto
  promise, and webcpp::webrtc's events are each posted to the `io_context`,
  and run when the run family resumes, never inside the event.
* The backend's timers are webcpp::asio's `steady_timer`, in the reactor's
  timer queue: they fire while the program runs its `io_context`.
* The program holds a work guard on the `io_context` for the page's life: a
  page that waits for its user, or for its peers, has no work of its own, and
  without the guard `run` would return.
* The page reaches {cpp} through the functions the program exports to it,
  through embind or `EMSCRIPTEN_KEEPALIVE`, and each only posts to the
  `io_context`. Nothing calls `run`, `poll` or `dispatch` from a JavaScript
  event: while `run` is suspended, an event sees the `io_context` as running
  in this thread, and a call of the run family there fails at its first
  suspension (webcpp::asio's guide, "Who may call it").

So nothing runs while nothing happens, a handler runs as soon as the run
family resumes after its event, and a turn of `max_handlers_per_turn`
handlers is followed by a yield, which lets the page render. A handler's
{cpp} exception propagates out of `run` to `main`, as it does natively.

[#trystero-browser-javascript]
=== How JavaScript reaches {cpp}

Every function the page calls with an event is made by webcpp::asio's
bridge, for a registration and a key that is never reused, and only posts to
the `io_context`: an object registers when it is made and removes its
registration when it is destroyed, so a late event for a destroyed object
finds nothing. A Web Crypto promise is awaited with webcpp::asio's
`browser::async_await`, whose settlement is posted the same way and whose
operation is outstanding work until it settles. webcpp::webrtc's objects
receive the page's WebRTC events through the same bridge. Their JavaScript
is linked into every program on emscripten by `/webcpp/asio//asio`: a
program includes no source file of trystero's.

Text that crosses into JavaScript is decoded straight from the WebAssembly
memory a view points into, `browser::js_string`, and text that comes back
is encoded straight into a string of the object's resource: no
`std::string` is made to carry either.

[#trystero-browser-exceptions]
=== No JavaScript exception enters WebAssembly

The browser backend makes every call into JavaScript that can throw, a
`WebSocket` constructor or `send`, a Web Crypto method, in JavaScript that
catches what it throws: a socket that cannot be made reports its close, and
a Web Crypto call is made inside an `async` function, so that what it throws
becomes the rejection of its promise, which the {cpp} turns into the error
its interface has. webcpp::webrtc's JavaScript catches the page's WebRTC
exceptions the same way. The bridge's functions catch what still escapes a
delivery, put WebAssembly's stack pointer back and report it, and with
exceptions a {cpp} exception is caught in {cpp}, which frees it. So a program
that uses the browser backend may be built with exceptions or without them,
and a peer's malformed message never stops the page's program.

[#trystero-browser-bounds]
=== What a page bounds

* A data channel message is read by webcpp::webrtc, a text as the UTF-8 it
  holds and a binary one as its bytes, and dropped on the executor when it is
  a text, as a peer can send, or larger than any room frame
  (`protocol::max_room_frame_bytes`): neither can be a frame. webcpp::webrtc
  bounds what it reads: a message past `max_message_size` (256 KiB), or
  unread messages past `max_received_bytes` (16 MiB), close the channel.
* A relay's text longer than 1 MiB (`protocol::max_relay_message_bytes`) is
  not copied into WebAssembly: the socket closes, and reports the close.
* A text that would take the socket's `bufferedAmount` beyond 4 MiB
  (`protocol::max_queued_relay_bytes`), as when a relay stops reading, drops
  the socket, which reports one close after the call. A page's `WebSocket`
  cannot ping, so the browser has no idle timeout, which the native backend
  has (<<trystero-native-relays>>).
* A page makes at most `browser::backend::max_peer_connections` (256) peer
  connections across all apps and rooms it serves, counted from their
  construction until the garbage collector frees them, as Chromium counts
  them against its own 500 (measured with headless Chrome: the 501st throws
  "Cannot create so many PeerConnections", and a closed one counts until a
  collection). It is the cap of the webcpp::webrtc runtime the backend owns,
  `runtime_options::max_peer_connections`, and webcpp::webrtc's census of
  the page counts every connection it makes, with any runtime. Beyond, the
  rooms report each negotiation they cannot start, and the rest of
  Chromium's count stays free for what the page makes without a room.

Peer connections, data channels and received frames use the app's resource;
relay sockets, their events, timers and sealed signaling texts use the
room's. Presence or reuse binds another room without making another peer
connection.

[#trystero-browser-page]
=== What a page needs

* A secure context: https, or http on `localhost` or `127.0.0.1`. Elsewhere
  `crypto.subtle`, which seals the signaling, does not exist, and every
  sealing operation fails with `error::backend_failure`.
* No threads: Emscripten's threads need a cross-origin isolated page, so
  trystero uses none. Its Asio is webcpp::asio's, built without threads when
  the program has no pthread ABI, and `main` runs it on the page's one
  thread.
* A suspension variant of webcpp::asio, which `/webcpp/trystero//trystero`
  brings: `webcpp-suspend=jspi`, the default, for a browser with JavaScript
  Promise Integration, or `asyncify` for any other. The `run` of `main`
  suspends in either, and a page loads a variant its browser runs: the
  chat's site is built in one, JSPI unless the build asks for
  `webcpp-suspend=asyncify` (<<trystero-building-examples>>).
* A program that runs its `io_context` from `main` for as long as the page
  lives, under a work guard: the `io_context` must outlive every room and
  object it serves, and its handlers run only while it runs.
* Boost.JSON's definitions, which a program links from `/webcpp//boost_json`,
  which `/webcpp/trystero//trystero` brings and which builds on emscripten
  as on every target.

[#trystero-browser-chat]
=== A page and its program

The chat example is a page whose room is {cpp}: the program joins and sends,
and the page only draws. It keeps the `io_context`, the backend and the room
for the page's life, and makes the action `chat` twice: once as
`std::string_view`, to receive a message as a view of its frame, and once as
`std::string`, to send by moving the text:

[source]
----
include::{examples}/chat/chat.cpp[tag=state]
----

The program joins the app and the room its user typed, and sets its
handlers; a received message goes from its frame straight into a JavaScript
string:

[source]
----
include::{examples}/chat/chat.cpp[tag=join]
----

`send_message` shows the message at once, and reports a failure in the
page's log:

[source]
----
include::{examples}/chat/chat.cpp[tag=send]
----

The page calls `join` and `send` from its own events, a form's submission;
each only posts the work to the `io_context`, which `main` runs:

[source]
----
include::{examples}/chat/chat.cpp[tag=calls]
----

They are what the program exports to the page, through embind:

[source]
----
include::{examples}/chat/chat.cpp[tag=bindings]
----

And `main` runs the `io_context`, under a work guard, for the page's life:

[source]
----
include::{examples}/chat/chat.cpp[tag=main]
----

Any Trystero JS page, or any other page of the chat, that joins the same app
and room is in the same chat (<<trystero-building-examples>>).
