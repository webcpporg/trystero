[#trystero-testing]
== Testing

[#trystero-testing-program]
=== Testing a program that uses trystero

A room needs relays and peers, and a test needs neither the network nor
another machine. The backend interface is the seam: a program's tests run its
rooms over a backend of their own, in memory, as trystero's own tests run
whole rooms over `test/support/memory_backend.hpp`, a backend whose Nostr
relays forward ephemeral events to matching subscriptions, whose peer
connections pair through their descriptions, whose data channels deliver in
order, and whose sealer opens only what was sealed under the same key, each
event posted to the `io_context`. It is in the namespace
`webcpp::trystero::test`, outside the library's public headers, and a
program may copy it.

The memory network identifies connection ends with `std::size_t` ids.
`on_made` records construction and ICE servers, and `peer_of` identifies the
paired end. A `filter` delivers, drops or holds frames; a held frame holds
all later frames from its sending end behind it, preserving channel order
until `release`. Deferred `open` calls open each end separately; `inject`
and `fail` supply malformed frames and transport failure.

With `channel_capacity` enabled, the channel queues bytes and drains up to
`drain_per_post` per post. It delivers a frame only after its last byte
drains, and `buffered` reports the exact unsent amount. Set `virtual_clock`
before making timers: `advance` fires due timers in order and runs ready
work between them; `step` and `poll_ready` give tests finer control. Timeouts,
backoffs and late frames are tested without wall-clock sleeps. Optional
fault hooks allocate outside the measured resources only when enabled;
the allocation test leaves them disabled.

A native test of the platform backend's own WebRTC binds its connections to
the loopback, `platform::backend_config::bind_address` set to
`"127.0.0.1"`, and names a STUN server where nothing answers,
`stun:127.0.0.1:9`, in place of Trystero's public ones: the loopback's host
candidate is then the only one, and it is enough. A page cannot bind, and
leaves `bind_address` empty (<<trystero-platform-config>>).

[#trystero-testing-library]
=== How trystero is tested

trystero's tests are under `test/`, each declared in `test/Jamfile`, and each
guarantee of <<trystero-guarantees>> names the tests that hold it. They run
on two targets: {n-tests} tests in all, {n-tests-native} natively and
{n-tests-emscripten} on emscripten, under node, each in both of webcpp::asio's
suspension variants, JSPI and Asyncify. The protocol, the rooms, the timer
and the allocation test run on both:

[listing]
----
include::{library-root}/test/Jamfile[tag=both-targets]
include::{library-root}/test/Jamfile[tag=allocation]
----

[cols="1,3",options="header"]
|===
| Test | What it checks

| the public headers
| Each compiled alone, on each target that builds it: the core, and the
  platform backend's `backend.hpp`, `entropy.hpp`, `sealer.hpp` and
  `websocket.hpp` with the backend's WebRTC, on both, natively against
  webcpp::webrtc's libdatachannel and OpenSSL and in a page over its own
  objects; and `platform/page.hpp`, on emscripten alone.

| `config`, `config_developer_defined`, `config_all_off`
| `<webcpp/trystero/config.hpp>` defines `WEBCPP_TRYSTERO_NO_EXCEPTIONS`
  exactly when webcpp has no exceptions (`WEBCPP_HAS_EXCEPTIONS` is not
  defined: the compiler has none, or the program defined
  `WEBCPP_NO_EXCEPTIONS`), and keeps it when a developer defines it for
  trystero alone in a build that has them.

| `protocol`
| The protocol against values Trystero JS 0.26.0 computed itself: topics,
  room tokens, the relay shuffle, sealed text, Nostr event ids, inline and
  chunked action frames, control frames, envelopes and presence, a JSON
  payload's numbers and key order, and the bounds of a signal's fields.

| `signaling`
| The signaling and the Nostr strategy alone: as an answerer, the signals
  Trystero JS 0.26.0's own signal handler published for the same offers,
  byte for byte, a signal or a relay's text read at its bound and
  dropped one byte past it, and a relay's text read 16 deep and dropped one
  level deeper.

| `room`
| Whole rooms in one process, over the memory relays: every payload format,
  100 KB transfers both ways, ping, passwords right and wrong, leaving and
  returning, a room moved over a joined one, ICE servers checked as WebRTC
  checks them, floods of announcements and of forged, replayed and reflected
  signals, a relay that closes at once or rate-limits, a three-peer mesh,
  coroutines and view handlers, JSON payloads read in the room's resource
  up to its bound, and a rejected document receive.

| `app_impl`
| Configuration copying and validation, a self id that is not UTF-8 set
  aside, resource ownership, weak room
  registration, shared adoption, stale replacement, reentrant adoption,
  last-user closure and quiet destruction with pending work.

| `connection`
| Shared transport routing, advertised token and kept-frame limits, binding
  detachment, departures and kicks, idle expiry and drain ordering.

| `memory_backend`
| Virtual timer ordering, cancellation, held-frame order, deferred opens,
  injection and failures, and byte-accurate buffering and drain.

| `shared`, `shared_no_exceptions`, `shared_hardened`
| Multiple apps and rooms with one connection per remote peer, adoption
  races, presence and reuse, room isolation, departures, idle connections,
  password-domain isolation, invalid room proofs, transient handshake recovery,
  fairness, bounds, a handshake message read at its bound and failing one
  byte past it, and resource ownership. The suite also runs without exceptions and with
  standard-library hardening; sanitizers check lifetimes and detachment.

| `allocation`
| Every allocation of two apps and their rooms goes through their resources
  (<<trystero-allocation-proof>>).

| `timer`
| The timer over webcpp::asio's `steady_timer`, which the platform backend
  makes on both targets: a wait fires once, in the timer's resource, and one
  cancelled, restarted or destroyed never fires, even when its expiry was
  already queued.

| `platform_backend`, `platform_sealer`, `platform_websocket_unreachable`,
  `platform_websocket_url`, and each `_no_exceptions`
| The platform backend on both targets, natively and on emscripten under
  node, which has the page's WebSocket and Web Crypto but no WebRTC. The
  backend itself keeps its own state, its copy of `bind_address`, its window
  of constructions and its own runtime, in `backend_config::memory`, none of
  it in the default resource, and gives it all back when it is destroyed
  (<<trystero-allocation-resource>>); its clocks are the standard library's,
  its randomness fills what it is given, differently each time, beyond a
  piece of its source too (65536 bytes in a page), its executor is the one
  it was given and its TLS context is made. The sealer opens what Trystero JS
  sealed with Web Crypto, seals a text that opens again in Trystero's form,
  takes a text sealed under another key, or no sealed text, for a wrong
  password, completes after the call that started it, never inside it, and
  completes each of two seals and two opens given in one call, which in a
  page wait while it imports its key; in a page without `crypto.subtle` it
  fails with `error::backend_failure`. A relay it cannot reach, of a URL the
  session refuses, `http://` and `https://` among them, reports exactly one
  close, after the call that made it, and so does one of a port on 127.0.0.1
  or `::1` where nothing listens, which is attempted: natively its TCP
  connection fails, and in a page node's `WebSocket` is made and closes
  before it opens. A relay's URL is read as a page reads it, and what a
  page's URL parser reads otherwise is refused, by the same rules on both
  targets.

| `platform_websocket`
| The relays' WebSocket natively, built with the standard libraries' checks,
  against Beast servers in the same process: it opens, sends in order,
  closes once, reaches a relay at an IPv6 address (where the kernel opens a
  socket of IPv6's family; elsewhere the case prints that it does not apply
  and checks nothing), opens over TLS with the relay's name sent (SNI)
  against a test authority, refuses a certificate for another name or of an
  authority not trusted, also with a program's context whose verify mode is
  `verify_none`, keeps a TLS context's error in the backend, drops a binary
  message, closes once when the connection ends during a write, and drops a
  relay that sends too much, stops reading or stops answering, while one
  that answers its pings stays.

| `platform_websocket_allocation`, `platform_websocket_allocation_no_exceptions`
| Natively, a relay's message allocates nothing outside the room's resource:
  from the send of a text to the receipt of its echo, ten times, the global
  `operator new` counts none on the room's thread
  (<<trystero-allocation-outside>>); and a relay that refuses the upgrade
  with a body of 4 MiB has its response's header read alone, the room's
  thread allocating less than 64 KiB until the close.

| `platform_peer_connection`, `platform_room`, and each `_no_exceptions`
| Natively, two connections of the backend's WebRTC, over webcpp::webrtc's
  libdatachannel, wired to each other, each handler on the executor, and
  whole rooms over the platform backend and real connections, bound to
  127.0.0.1. A controlled executor holds the offerer's events to prove
  pre-handler FIFO delivery, a 65th message read ahead of the posted flush,
  handler replacement and destruction, the 64-frame and 10-second bounds,
  and allocation and release through the connection's resource; a peer of
  webcpp::webrtc's own sends a text, which is dropped between two frames;
  malformed candidates and descriptions fail without throwing, and so does a
  candidate one byte past its bound, which at the bound is added; a local
  candidate that is not UTF-8 is not written; the backend
  makes at most its budget in a minute, holds at most its runtime's cap at
  once, and leaves out a URL libdatachannel cannot parse. Both run once more
  without exceptions.

| `platform_page_websocket_bound`, `platform_page_websocket_late_events`,
  `platform_page_websocket_ingress`, `platform_page_websocket_tls`,
  `platform_page_data_channel`, `platform_page_peer_connection`,
  `platform_page`, `platform_page_call`, `platform_page_handlers`,
  `platform_page_sealer`, `platform_page_sealer_allocation`,
  `platform_page_relay_allocation`, and each `_no_exceptions`
| The platform backend in a page, on emscripten under node, each test's
  `main` running its `io_context` as a page's program does: the relays'
  WebSocket, its bound on what a relay holds unsent, both the session's own
  queue and the page's `bufferedAmount`, which webcpp::beast's send limit
  bounds, and its silence once dropped; its refusal of a text past 1 MiB that
  a relay sends in the same task as its open, and of a binary message; a
  program's context of `tls_client`, whose verify mode is `verify_none`,
  reaching a `wss://` relay, and the contexts a page cannot honour refused;
  what a relay's connection and each of its messages allocate outside the
  room's resource, exactly; over webcpp::webrtc's browser
  objects and a page's `RTCPeerConnection` of the test's, a data channel's
  refusal of what is no frame, and the page's peer connections, made or
  refused, webcpp::webrtc's census of them and the backend's window of
  constructions, which holds in a page as natively; and the shape of a
  page's program, whose work guard keeps a page with no room yet running,
  and whose `platform::page_call` functions, called from JavaScript while
  `run` is suspended, return at once, only post, and reach the room, twice
  in a row under Asyncify too, while a value of the wrong type is ignored
  and breaks nothing; a call through a function the page kept after its
  `page_call`, or its `io_context`, was destroyed reaches nothing, and the
  handler reads the page's value as it is when it runs, and a number within
  its range; the relay socket's and the sealer's handlers run outside the
  page's events; a page whose `crypto.getRandomValues` throws or is missing
  has no randomness and fails a seal, and one whose `crypto.subtle` settles
  with something other than an `ArrayBuffer` fails a seal and an open, with
  `error::backend_failure`, no JavaScript exception entering WebAssembly; and
  a seal and an open allocate nothing outside the room's resource, neither
  with `operator new` nor with the C library's functions.
|===

The platform backend's tests run on each target that builds them, and once
more without exceptions (<<trystero-platform-exceptions>>), as a program
that uses the backend may be built, but for `platform_websocket`, which
runs once, with the standard libraries' checks:

[listing]
----
include::{library-root}/test/Jamfile[tag=platform]
include::{library-root}/test/Jamfile[tag=page]
include::{library-root}/test/Jamfile[tag=no-exceptions]
----

From the root of a webcpp checkout, with libsecp256k1 found
(<<trystero-building>>), each of these builds and runs the tests,
natively, under AddressSanitizer and UndefinedBehaviorSanitizer, and on
emscripten:

[source,bash]
----
b2 libs/trystero/test
b2 libs/trystero/test address-sanitizer=norecover undefined-sanitizer=norecover
b2 toolset=emscripten libs/trystero/test
----

The chat page's program is linked and never run, since it is a page; the
quick start and the programs of the appendix "Differences" run over a relay
of their own in the lane `relayed` (<<trystero-testing-twins>>), and the one
of them that needs no relay with the ordinary examples, `b2
libs/trystero/example`. b2 compares timestamps, so a result that counts is
built from scratch, with `b2 -a`.

[#trystero-testing-lanes]
=== The oracle and the interop lanes

Two lanes of trystero's own, declared in `test/oracle/Jamfile`, check it
against Trystero itself, pinned at 0.26.0 by `test/oracle/package.json` and
`package-lock.json`, with Node, run as `node --conditions=development`:

[listing]
----
include::{library-root}/test/oracle/Jamfile[tag=oracle]
----

`oracle`, which names no target, runs Trystero's own functions over the
inputs of `test/fixtures/cases/protocol.json` and checks that they still
write `test/fixtures/expected/expected.json` byte for byte, the values the
`protocol` and `platform_sealer` tests reproduce, and runs the twins of the
examples (<<trystero-testing-twins>>); `update-expected` is the only writer
of the expected values and of each divergent twin's output.

[listing]
----
include::{library-root}/test/oracle/Jamfile[tag=interop]
----

`interop`, natively and on emscripten, meets each {cpp} peer, the native one
as a process and the browser's in headless Chrome, with Trystero JS peers in
Chrome, over an in-memory Nostr relay on 127.0.0.1 that verifies every
event's id and signature as a public relay does. Its scenarios: the {cpp}
peer offering; Trystero JS offering, with a password; a Trystero JS peer that
also sends malformed candidates, or text messages on its data channel; a
first relay to which no WebSocket can be made; a {cpp} peer given a TURN
server without credentials; a watcher without the key that answers every
offer with garbage in the other peer's name, that resends a sealed answer
and offer it recorded, and that sends the {cpp} peer its own sealed offer
back, which the {cpp} peer must refuse; a flood of announcements and of
unsealed offers from fresh peer ids; a relay text longer than 1 MiB; a {cpp}
peer and a Trystero JS page each in two rooms of one app, sharing one
connection and one peer id per app; a wrong password;
and a mesh of three. The native peer meets three more: a room
moved over the joined one, which must leave it as destroying it does; a
relay that ends the connection just as the peer writes, which twelve peers in
turn must survive; and the driver's own check that a peer killed by a signal
is named at once.

The shared-connection scenarios run in both lanes:

. Two rooms exchange chat and 100 KB files both ways on one adopted,
  connected transport.
. A third room joins later through presence on that transport.
. Rooms the JS page joined first bind when the {cpp} app joins them later.
. A peer can enter another room of a passwordless app by token, while a
  protected app with another password and self id shares no connection or
  presence with it, in either id order.
. Either side leaves one room while the other keeps exchanging, making
  no connection.
. Leaving every room closes the transport after the configured idle time.
. An authenticated peer sending wrong room proofs in both id orders gives
  paced lower-id reports while
  the other room keeps exchanging over the same connection.
. A 5,000-message flood in one room leaves pings in another completing
  within 2 s.
. A held handshake frame recovers in both id orders after one timeout,
  without a false password report; the other room keeps exchanging.

The {cpp} peers accept `room2Delay` and `room3Delay` in milliseconds; the JS
page also accepts `room2Delay`. These delayed joins establish the first room
before a shared-binding scenario begins;
the proof-pacing scenario first authenticates the shared password domain,
then corrupts room proofs after the initial announcement burst.

The adoption scenarios allow crossed duplicates to retry, but fail with
connection counts if either side constructs more than four. Transient
recovery accounts for JS reuse during the higher id's dropping window
(<<trystero-protocol-limitations>>).

Every peer gathers its ICE candidates on the machine alone: the {cpp} peers
get `stun:127.0.0.1:9` in place of Trystero's public STUN servers, the
native peer binds its connections to 127.0.0.1, and the Trystero JS peers
have no ICE server. Chrome is the one `CHROME` names, else on macOS
Playwright's `chrome-headless-shell`; the continuous integration names Chrome
for Testing's `chrome-headless-shell`, at the version webcpp pins. Each driver
is bounded by 2,400 s, beyond its scenarios' own limits, so that a scenario that
does not complete fails by name with what each peer saw.

[source,bash]
----
b2 -a libs/trystero/test/oracle//oracle
b2 -a --dump-tests --out-xml=native.trystero.interop.xml libs/trystero/test/oracle//interop
b2 -a --dump-tests --out-xml=emscripten.trystero.interop.xml toolset=emscripten libs/trystero/test/oracle//interop
----

[#trystero-testing-twins]
=== The examples over a relay, and their twins

The quick start and each program of the appendix "Differences"
(<<trystero-differences-shown>>) meet over a Nostr relay of their own, the
interop's `test/oracle/interop/relay.mjs` on 127.0.0.1, in the lane
`relayed`, natively, which `example/Jamfile` declares: its driver,
`example/run_over_relay.mjs`, starts the relay, runs the program with the
relay's URL in its environment, `TRYSTERO_RELAY_URL`, which the program
reads, and passes when the program exits with 0 having printed its
`.expected`.

[listing]
----
include::{library-root}/example/Jamfile[tag=quick-start]
include::{library-root}/example/Jamfile[tag=differences]
----

Each of these programs has its twin in `test/oracle/twins/`, the same
program on Trystero 0.26.0, which the oracle lane runs through
`test/oracle/run_twin.mjs`: a relay of its own, its URL in
`TRYSTERO_RELAY_URL`, and the twin, whose output must be the program's
`.expected`, or, for a difference, its own `.expected`, which must differ.
The twins agree with {n-twins-agreeing} of the programs and diverge from
{n-twins-divergent}; {n-examples-without-twin} have none, each with its
reason in `test/oracle/twins/without-twin.txt`: the chat, a page that prints
nothing, and a difference whose original has no counterpart.

Trystero JS has one self id per page, so a twin whose room meets a peer, as
a {cpp} program's second app does, runs that peer as a second page, a worker
thread with Trystero's modules of its own (`test/oracle/page.mjs`). Node has
no WebRTC: Trystero JS takes werift's `RTCPeerConnection` as `rtcPolyfill`,
the WebRTC for Node that Trystero 0.26.0's own README names, pinned at 0.24.4
in `test/oracle/package.json` for the twins alone. The {cpp} programs whose
apps meet bind their connections to 127.0.0.1 with `stun:127.0.0.1:9`, and
the twins have no ICE server, so every peer stays on the machine.

[source,bash]
----
b2 -a --dump-tests --out-xml=native.trystero.relayed.xml libs/trystero/example//relayed
b2 -a libs/trystero/test/oracle//twins
----

[#trystero-testing-container]
=== The container lanes

Two lanes of the continuous integration, `gcc-14` and `clang-linux-18`, build
and run the unit tests with GCC 14 and with clang 18 against
`libstdc{plus}{plus}` in a Linux container, Ubuntu 24.04, with `docker run`
and the network `none`, which leaves the loopback alone: every test passes,
which shows that none reaches beyond the machine
(<<trystero-invariant-6,guarantee 6>>). libsecp256k1 is installed before
running the container. B2 builds the pinned OpenSSL, libdatachannel and
nested source dependencies inside the container with the lane's compiler,
runtime and static link configuration. These builds need no network access.

[#trystero-testing-provider]
=== The common OpenSSL provider

The native `provider-integration` lane builds and runs one application that
uses Asio TLS, Beast and Trystero's platform backend together, natively. It
compares the compiled OpenSSL version with the loaded implementation, makes
its WebRTC state through trystero's backend, a peer connection and a data
channel, and checks the backend's relay TLS context, all over the one
provider. The run is bounded to 45 seconds and uses the threaded release
profile, with exceptions as the build asks. The superproject's source
dependency tests also check that the final Unix executable has no dynamic
OpenSSL or libdatachannel provider, that each static archive occurs once and
that dependent archives precede OpenSSL in the link order.

[#trystero-testing-report]
=== The test matrix

The continuous integration runs trystero's tests in lanes, one toolset each,
and its own lanes, the oracle once, the examples over a relay natively, as
`native.trystero.relayed`, and the interop natively and on emscripten, as
`native.trystero.interop` and `emscripten.trystero.interop`, plus the
native `provider-integration` lane for the common TLS provider.
Each lane builds from scratch and records what b2 built and ran; webcpp's
`tools/report/report.py` merges the files of every lane into a matrix, where
each cell says whether that program passed in that lane, or how it failed.
The matrix is published with the documentation, at
https://webcpporg.github.io/report/.
