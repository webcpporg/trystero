[#trystero-design]
== Design

[#trystero-design-layers]
=== Layers

[cols="1,2,3",options="header"]
|===
| Layer | Headers | Knows

| Protocol
| `protocol/*.hpp`
| pure functions over bytes and text: no I/O, no platform

| Backend interface
| `backend.hpp`
| the WebSocket, peer connection, data channel, timer and AES-GCM sealer a
  platform provides

| App
| `app.hpp`, `detail/app_impl.hpp`, `detail/connection.hpp`
| one identity, the room registry, shared connections and their routing

| Room
| `room.hpp`, `detail/*.hpp`
| the Nostr strategy, signaling, bindings, action wire and room API

| Backend's WebRTC
| `webrtc/*.hpp`
| webcpp::webrtc's peer connections and data channels, and trystero's
  policies over them, on both targets

| Platform backend
| `platform/*.hpp`
| webcpp::webrtc, webcpp::beast (natively Boost.Beast, in a page its
  `WebSocket`), Boost.URL, webcpp::asio's timers, and per target the sealer
  and the randomness: OpenSSL natively, Web Crypto and
  `crypto.getRandomValues` in a page; and, in a page, `page_call` and `js_string`
|===

Everything above the backend interface is the core, which builds on both
targets: the same room runs over the browser's WebRTC and libdatachannel's,
both through webcpp::webrtc, and over the memory relays of the tests
(<<trystero-testing>>). The core never includes the platform backend, the
backend's WebRTC, webcpp::webrtc, libdatachannel, OpenSSL or Emscripten: a
boundary of the library's own, which webcpp's lint checks, keeps it so. Its
Asio is webcpp::asio: natively Boost.Asio itself, on emscripten the backend
webcpp::asio ships, whose `io_context` webcpp::webrtc's browser objects
deliver their events to.

[#trystero-design-sharing]
=== Connections shared by the rooms of an app

[cols="1,3,2,1",options="header"]
|===
| Object | Owns | Lives | Resource

| `app`
| A reference to `detail::app_impl`, counted as one user
| While the user keeps its handle
| None

| `detail::app_impl`
| Configuration and immutable password, self id, logger, room registry by token and id, connections and user count
| While any shared reference lives; its last user closes its connections
| App's

| `detail::connection`
| One peer's connection and channel, advertised tokens, kept frames, idle timer and plain pointers to bindings and their drain order
| From adoption until its end
| App's

| `detail::binding`
| One room's use of a connection: a weak reference, drain waiters and delivery to its room
| Until detachment, owned by its room's peer state
| Room's

| `room`
| A reference to `detail::room_impl`
| While the user keeps its handle; destruction leaves
| None

| `detail::room_impl`
| Signaling, strategy, actions, peers, bindings, handlers, rebinding counts, backoffs and a shared reference to the app
| Until its state and pending operations end
| Room's, the app's by default
|===

* A room holds the app strongly; the app reaches rooms weakly. A binding
  holds its connection weakly, and the connection holds plain pointers to
  bindings. Detachment removes those pointers and every drain registration
  before returning. Ending a room removes its registry entry, so the app
  keeps no allocation of that room's resource after it ends, and no cycle
  keeps the objects alive.
* Sharing is scoped by the `app` the user constructs, with no registry
  outside it and no static state keyed by the backend. Two apps with the
  same application id in one process are two peers. Each app has one
  immutable password. Different passwords use separate apps with distinct
  self ids, so their connections, tokens and presence are never reused.
* The action wire continues to write its room token and send through a
  `channel_link`. The binding implements that link: each room keeps its
  own actions, transfers, queues and bounds.

[#trystero-design-backend]
=== Why abstract classes for the backend

The backend is a handful of abstract classes rather than template
parameters. Each of its operations is a call into JavaScript or into a
network stack, so a virtual call costs nothing measurable, while the room's
code stays free of templates over the platform and of `#ifdef`, and the
tests' memory relays and the platform backend are interchangeable at run
time. Every handler a backend invokes runs on the room's executor, after the
call that caused it has returned, never inside it: the room calls these
operations from inside handlers whose state a completion run there would
change under them.

One class, `platform::backend`, implements the interface on both targets,
in place of a backend of each: the owner's decision 3 of trystero's
refactor (2026-11-14), since webcpp::asio, webcpp::beast and webcpp::webrtc
give both targets one interface, where everything but WebRTC was written
twice. The abstract classes stay, for the memory relays, which run whole
rooms on both targets where node has no WebRTC, and for the interop's native
peer, which wraps the platform backend. Only the sealer and the source of
randomness are chosen per target, by `WEBCPP_TARGET_EMSCRIPTEN`, until
webcpp::crypto exists (<<trystero-platform>>).

[#trystero-design-webrtc]
=== Why webcpp::webrtc

The platform backend's WebRTC is webcpp::webrtc's: the W3C's API in Asio's
model, one interface natively, over libdatachannel's C API, and in the
browser, over the page's own `RTCPeerConnection`. It replaces the backend's
own wrappers of each, so that trystero keeps only its policies over WebRTC,
the same on both targets. In the browser it binds the page's objects, not
libdatachannel's WebAssembly port, datachannel-wasm, which has no media and
hides the `RTCPeerConnection` it wraps; natively its C API lets the backend
work without exceptions. The backend interface stays a handful of abstract
classes (<<trystero-design-backend>>): the rooms of the tests run over the
memory relays, on both targets, where node has no WebRTC, and the interop's
native peer wraps the platform backend's connections.

[#trystero-design-backend-webrtc]
=== The backend's WebRTC

The platform backend makes its peer connections and data channels the same
way on both targets, in `<webcpp/trystero/webrtc/peer_connection.hpp>` and
`data_channel.hpp`: `webrtc::peer_connection` and `webrtc::data_channel` hold
webcpp::webrtc's `basic_peer_connection` and `basic_data_channel` over a
`std::pmr::polymorphic_allocator` on the app's resource, keep a wait of each
kind pending on them, re-armed on the executor, and report what each
completes with through the backend interface. What is trystero's, and stays
in them, over webcpp::webrtc:

* The states. A connection reports one state, which merges its connection
  state and its ICE state as a page sees both: failed when either failed,
  then closed, disconnected, connected (or ICE completed), connecting (or ICE
  checking), and new.
* The candidates. A local candidate leaves as the JSON of an
  `RTCIceCandidateInit`, the form Trystero JS adds with `addIceCandidate`; a
  remote one is read from that JSON, at most 16 KiB of it. Natively it
  carries `sdpMid` and an `sdpMLineIndex` of 0, and no user name fragment, as
  libdatachannel gives none; a candidate whose text is not UTF-8, which JSON
  cannot carry, is not reported.
* The frames. A channel reads every message as it comes, with
  `async_receive`, into a vector of the app's resource, which the message
  handler then owns. A text message, as a peer can send, or a binary one
  larger than any room frame, is dropped there, on the executor: neither can
  be a frame. What reaches the executor is bounded by webcpp::webrtc: a
  message is at most `max_message_size`, 256 KiB, which natively
  libdatachannel cuts a longer one to, and past which in the browser, or past
  16 MiB of unread messages, the channel closes. A binary payload moves when
  its message buffer and the room use the same resource, and is copied once
  otherwise; chunked transfers assemble their buffer in the room's resource.
* The frames no room has read. Valid binary frames that arrive before the
  message handler is installed wait in a FIFO in the app's resource. The
  queue holds at most 64 frames for at most 10 seconds from its first frame,
  Trystero's pending-data bounds. Overflow or expiry closes the channel;
  closing or destroying it discards the pending frames. The backend's timer
  invalidates an expiry already queued when the queue drains or closes.
  Installing a receiver posts delivery on the executor with the app's
  allocator. It never calls the receiver inline, and delivery checks the
  current handler and channel before each frame, so a handler may replace
  itself or close the channel. A message already read ahead of that delivery
  drains older frames first when a receiver is available.
* The pace. The channel reports the buffered amount falling to 64 KiB, after
  a send left it above, as `onbufferedamountlow` does.
* The caps. The backend makes at most
  `backend_config::max_peer_connections_per_minute` connections in any
  minute, on both targets, its own policy against floods
  (<<trystero-platform-config>>): in a page a collection frees closed
  connections from the census, after which only this window bounds how fast
  a flood makes new ones. The `runtime` of webcpp::webrtc caps the
  connections alive at once, the backend's own or the program's
  (<<trystero-platform-runtime>>), in a page over the page's census
  (<<trystero-platform-bounds>>).

[#trystero-design-text]
=== Text is a view, a copy is a decision

A parameter that only reads text is a `std::string_view`, bytes are a
`std::span`, and a string is used where something must own the text: a map
key, a member, a capture of a handler that runs later.

* The digests the protocol takes are fed the parts of their input: nothing is
  concatenated to hash it.
* Every JSON text is webcpp::document's. Signals, relay messages, handshake
  messages and candidates are parsed by `webcpp::document::parse` into a
  `webcpp::document::pmr::document` of the room's or the app's resource,
  which holds its image and the parse's working state, and read as views
  into it; each caller bounds its text, and the image grows to at most
  twice that bound and 64 KiB (<<trystero-protocol-json>>). The JSON the room
  writes goes field by field into one reserved buffer, its strings quoted by
  `webcpp::document::quote`, the quoting of `JSON.stringify` itself, and a
  Nostr event's id is hashed over those same bytes. Building each text as a
  document and writing it again was set aside: it would copy every string
  into a node of some 200 bytes, then write it once more. trystero keeps no
  owner of its own around a document: an earlier one, a buffer of the
  room's resource under an external document, retried twice as large when a
  parse filled it, gave way to document's own allocator, whose image grows
  in place.
* A JSON payload is a document of document's own types,
  `webcpp::document::document` in the standard allocator, the user's
  choice, and `webcpp::document::pmr::document`, received in the room's
  resource, as a text is a `std::string` or a `std::pmr::string`. A handle
  keeps document's rule: it refers to its document object, and moving the
  document invalidates it.
* A frame is written once, inside its room envelope, and shared by every
  target; a received frame becomes the buffer of the message delivered from
  it, and a view handler reads it in place.
* A sentence of the log is composed only when there is a sink.

The asynchronous operations are the exception, for the reason
<<trystero-usage-tokens>> gives.

[#trystero-design-dependencies]
=== Dependencies

trystero builds on webcpp::asio, and its platform backend on webcpp::webrtc
and webcpp::beast. `/webcpp/trystero//trystero` is the rooms alone: it brings
`/webcpp/asio//asio`, which links embind on emscripten, and on no target
webcpp::webrtc. A program names `/webcpp/trystero//platform` on both
targets, which adds the backend to the rooms: `/webcpp/webrtc//webrtc` and
`/webcpp//boost_url` on both; natively webcpp::webrtc's libdatachannel,
under the MPL 2.0, and OpenSSL, under the Apache License 2.0, and for the
relays `/webcpp/beast//tls` and `/webcpp/asio//tls`, whose embedded
authorities a program may trust in place of the system's; in a page
`/webcpp/beast//browser`, over the page's `WebSocket`. Neither libdatachannel
nor OpenSSL is in a page's program, as OpenSSL is optional for Asio.
