[#trystero-native]
== The native backend

Natively, `native::backend` implements the backend interface over
webcpp::webrtc for WebRTC, which natively is
https://github.com/paullouisageneau/libdatachannel[libdatachannel]'s
(<<trystero-design-backend-webrtc>>), webcpp::beast for the relays' WebSockets,
natively Boost.Beast's, OpenSSL for TLS and AES-GCM, and Asio's timers. A native room is the
same room as a browser's or Trystero
JS's: they meet over the same relays and exchange the same frames. One
backend serves every app and room of the program, with separate app
objects and distinct self ids for different passwords, beside the executor it runs
on, and a native program runs that executor's `io_context` itself, blocking
on it or polling it (<<trystero-quick-start-native>>).

[#trystero-native-exceptions]
=== Exceptions

trystero raises no exception of its own, and the native backend works with
exceptions and without them, as the rest of trystero does. libdatachannel
reports errors by throwing, but webcpp::webrtc calls its C API, which catches
what it throws and returns a code: a refused description, candidate or
channel completes with `error::backend_failure`, a connection the platform
refuses is not made, and no exception crosses into trystero.

`<webcpp/trystero/config.hpp>`, which every header includes first, defines
`WEBCPP_TRYSTERO_NO_EXCEPTIONS` when webcpp has no exceptions
(`WEBCPP_HAS_EXCEPTIONS` is not defined: the compiler has none, or the
program defined `WEBCPP_NO_EXCEPTIONS`); a developer may define it for
trystero alone in a build that has them. It changes nothing in trystero's
behaviour. No function of the backend throws, its constructors included: when
OpenSSL cannot make the relays' TLS context, the backend keeps the error as a
value, which `tls_context()` returns, and every `wss://` relay reports a
close, as an unreachable one does (<<trystero-native-relays>>).

[#trystero-native-threads]
=== Threads

libdatachannel delivers its events on threads of its own. Neither
webcpp::webrtc nor the backend runs a handler there: webcpp::webrtc posts each
event to the room's executor, through a weak reference, so an event that
arrives after its object is gone does nothing. Every handler of the room and
every completion runs on the executor, as in the browser. An application
that runs the `io_context` on several threads gives the app a strand, shared
by all its rooms.

If a transport closes during adoption, before the room obtains a binding,
the room forgets that negotiation and restarts announcements. Its later close
event cannot leave signaling marked connected with no binding.

[#trystero-native-libdatachannel]
=== What the backend asks of libdatachannel

What libdatachannel does is webcpp::webrtc's: its C API, which works without
exceptions, automatic negotiation off, so that an offer or an answer exists
only when the signaling asks for one, as in the browser, and every object it
hands out held until its owner lets it go. The backend adds:

* Its connections bind to `backend_config::bind_address`.
* A TURN URL with a user name and a credential is written
  `turn:user:credential@host`, the form libdatachannel parses
  (webcpp::webrtc's `ice_server`).
* A URL libdatachannel cannot parse, as a `stuns:` one, a scheme it does not
  know, is left out of the connection, each URL being tried alone, where a
  browser refuses the whole connection.
* What libdatachannel allocates inside itself is libdatachannel's
  (<<trystero-allocation-outside>>).

[#trystero-native-runtime]
=== The runtime

webcpp::webrtc's `runtime` holds what libdatachannel keeps for the whole
process, its threads and its global state, and caps the peer connections
alive at once. A native backend makes one of its own, with
`backend_config::runtime`, or takes the program's: `native::backend(ex,
runtime, config)`, or `native::backend(ex, tls, runtime, config)` with the
program's TLS context too (<<trystero-native-relays>>). Each of its connections and channels keeps that runtime
alive, so that one which outlives the backend, in a handler the
`io_context` still holds, never outlives the runtime. A process holds one
runtime at a time, since libdatachannel's state is the process's: a program
with several native backends at once, or that uses webcpp::webrtc beside
trystero, makes one `webcpp::webrtc::runtime` before its `io_context` and
gives it to each.

[#trystero-native-config]
=== Its configuration

`native::backend_config` is what the backend makes its peer connections
with, beside the app's `ice_servers`:

[cols="1,3",options="header"]
|===
| Member | What it is

| `bind_address`
| The local address every peer connection binds to, as `"127.0.0.1"`; empty
  means every interface but the loopback. Bound to the loopback, the peers
  of one machine connect with no other network, which a test wants; a peer
  bound there reaches no other machine.

| `max_peer_connections_per_minute`
| The most peer connections the backend makes in any minute, for every room
  in every app it serves together, 256: beyond, it makes none, and a room reports each
  negotiation it cannot start. A room makes at most 64 in any 57 s however
  its peers behave (<<trystero-protocol-bounds>>), so the default lets four
  rooms do so at once. A connection still counts against its negotiating
  room's 57 s window after adoption by the app; presence and reuse make none.

| `runtime`
| What the backend's own webcpp::webrtc runtime is made with,
  `webcpp::webrtc::runtime_options`: its `max_peer_connections`, the most
  connections alive at once, 256 by default, beyond which the backend makes
  none and a room reports each negotiation it cannot start, and a connection
  gives its place back once it is gone; and `thread_pool_size`,
  libdatachannel's threads, its own default when 0. Unused when the backend
  is given the program's runtime (<<trystero-native-runtime>>).

| `relay_limits`
| What the relays' WebSockets tolerate of a relay that stops reading or
  answering, `native::websocket_limits` (<<trystero-native-relays>>).
|===

[#trystero-native-relays]
=== The relays

The relays are reached over webcpp::beast, natively Boost.Beast's own
WebSocket: `ws://` in the clear, `wss://` over TLS. Each connection is a
chain of Asio operations on the room's executor (resolve, connect, TLS, the
handshake, then one read after another, and one write at a time), whose
handlers carry the room's allocator, so that what Asio and Beast allocate for
them, the read buffer among it, is in the room's resource
(<<trystero-allocation>>). The WebSockets are Beast's rather than
libdatachannel's own, so the relays run on the room's executor like
everything else.

A relay's URL is read with Boost.URL, as a page's `WebSocket` reads it: the
scheme in any case, a host name in lower case and with its escapes decoded,
an IPv6 address in brackets (`ws://[2001:db8::1]:7447/`), whose address
without them is what the resolver looks up, and the scheme's port when the URL
names none. A URL of another scheme, without a host, with a user name or a
fragment, or with a port beyond 65535, is refused; the relay reports a close,
as an unreachable one does, and the room retries it later as it would any
other.

Over TLS the connection names the relay's host to the server (SNI) when it is
a name, never when it is an address, and checks the relay's certificate
against the URL's host, a name or an address. By default the backend makes
its TLS context with `native::make_tls_context()`: TLS 1.2 or newer, and the
system's certificate authorities, those OpenSSL's default verify paths name.
A relay whose certificate does not verify is unreachable, and the room
retries it later. An application that trusts other authorities makes its
context and gives it to the backend: webcpp's embedded Mozilla roots, which
read no file of the system, with `webcpp::asio::make_tls_client_context()`,
or a private authority with `webcpp::asio::make_tls_client_context(pem)`:

[source]
----
include::{library-root}/test/native_websocket_test.cpp[tag=embedded-roots,indent=0]
----

The backend takes the context as `make_tls_client_context` returns it, a
`boost::system::result`: one that holds an error, as when OpenSSL cannot
make the backend's own, is kept, `tls_context()` returns it, and every
`wss://` relay reports a close while the `ws://` ones are still reached. No
constructor throws. `tls_context()` also gives the context itself, which an
application may configure further before the backend connects to a relay.

A relay is a third party, and the backend bounds what one can make the room
hold:

* A text longer than 1 MiB (`protocol::max_relay_message_bytes`) closes the
  connection before it is copied, as in the browser.
* A relay that stops reading is dropped once the text held unsent for it
  would pass 4 MiB (`websocket_limits::max_queued_bytes`, which is
  `protocol::max_queued_relay_bytes` on both backends).
* A relay that stops answering is dropped once `idle_timeout` (30 s) passes
  with its keep-alive ping unanswered: halfway through, the connection sends
  a ping. The timeout counts bytes received, and a ping waits for the write
  in flight, so a relay that reads under about 2 KB/s is closed during a
  64 KiB text. Signaling texts are 2 to 4 KB, so a real room meets it only
  with a relay slower than about 200 B/s.

Each drop reports one close, and the room reconnects with its backoff
(<<trystero-protocol-discovery>>). A page has no idle timeout: its
`WebSocket` cannot ping (<<trystero-browser-bounds>>).
